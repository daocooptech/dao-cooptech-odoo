# ДАО КООПТЕХ — модули Odoo

Собственные модули платформы «ДАО КООПТЕХ» для Odoo. Работают на российском дистрибутиве **Rudoo 19.0** (консорциум под координацией ИСП РАН), но от него не зависят жёстко: где можно, опираемся на ядро Odoo.

Прототип платформы и требования — [daocooptech/dao-cooptech](https://github.com/daocooptech/dao-cooptech). Там же `docs/odoo-map.md` — карта соответствия: по каждому экрану прототипа сказано, берём ли мы готовое, расширяем стандартное или пишем своё.

## Что здесь есть и почему так мало

Из шестидесяти с лишним экранов прототипа своих моделей выходит одиннадцать. Всё остальное закрывается ядром Odoo и модулями Rudoo — договоры, УПД, акт сверки, доверенности, авансы, согласования, документооборот там уже написаны и локализованы.

Главный принцип: каждая сущность попадает в одну из трёх корзин — **ложится на стандарт** (не изобретать), **стандарт плюс поля** (наследование, не копия), **своя модель** (кооперативная специфика). Если своих моделей получается больше одиннадцати, значит стандартную просто не нашли.

| Модуль | Что делает |
|---|---|
| `coop_base` | Членство в организации, роли и права уровня записи |
| `coop_theme` | Палитра, шрифты и скругления платформы в интерфейсе Odoo |
| `coop_extensions` | Каталог расширений: установленные и общий, с публикацией своих |
| `coop_demo` | Данные для стенда: кооперативы, люди, ресурсы, проект, сделка |
| `forks/l10n_ru` | Форк плана счетов OCA, портированный на 19.0 — см. `forks/README.md` |

## coop_base

**Членство — единственное, чего в Odoo нет по смыслу.** `res.partner` описывает, с кем мы имеем дело, но не отношения членства: у одного человека членство сразу в нескольких кооперативах, у каждого свой устав, свой пай и свой порядок выхода. `hr.employee` описывает трудовые отношения, а пайщик не работник — он совладелец и может в кооперативе вообще не работать.

Три вещи заложены сразу, потому что дописать их потом дороже, чем сделать:

**Право голоса — отдельное поле, а не производное от пая.** Один член — один голос независимо от размера вклада. Поле сделано явным, чтобы правило было видно в данных, а не подразумевалось.

**Приём и прекращение членства требуют основания.** Это компетенция органа управления, и запись без ссылки на протокол не может стать действующей — проверка стоит на переходе в состояние «действующее».

**Ревизионная комиссия наследует пайщика, а не правление, и не имеет права записи.** Проверяющий, который может править проверяемое, — это не проверка. Правление, в свою очередь, ведёт членство только своей организации: в федеративной сети возможность править чужой состав не теоретический риск.

Членство прекращается, а не удаляется: права на удаление нет ни у кого, включая правление.

## Посмотреть онлайн

[![Открыть в Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/daocooptech/dao-cooptech-odoo)

Кнопка поднимает стенд в облаке: Odoo 19, модули Rudoo, российский план
счетов, наши модули и данные. Первая сборка занимает около десяти минут —
качаются модули и собирается база; дальше открытие занимает секунды.

Когда стенд поднимется, во вкладке **Ports** появится ссылка на порт 8069.
Порт открыт всем: ссылку можно послать кому угодно.

Вход: `admin` / `admin` — рабочая группа платформы, `vodyanov` / `vodyanov` —
пайщик и член правления кооператива «Шукты». Разница видна сразу:
администратору платформы членство в кооперативах **не показывается вовсе**,
и это не недоработка, а решение — платформа обслуживает сеть, а не
участвует в ней.

На стенде нет ничего настоящего: выдуманные кооперативы, выдуманные люди,
выдуманные сделки. Пароли тоже стендовые и для боевой установки не годятся.

## Как запустить

Стенд разворачивается рядом, вне этого репозитория. Порядок `addons_path` важен:

```
addons_path = .../coop-addons, .../rudoo-addons, .../odoo/addons
```

Сначала наши модули, потом Rudoo, потом ядро — так при совпадении имён наше перекрывает чужое, а не наоборот.

```bash
./stand.sh init                 # кластер PostgreSQL на 5433
./stand.sh deps                 # зависимости в venv
./stand.sh install coop_base    # база rudoo и модуль
./stand.sh up                   # http://127.0.0.1:8069
```

## Русская локализация

```bash
./stand.sh install coop_base            # наши модули
python odoo-bin -c odoo.conf -d rudoo --load-language=ru_RU -i translation_helper
```

Дальше язык ставится пользователям, компании и **шаблону нового пользователя**
— иначе каждый заведённый потом получит английский и будет переключаться руками.

**Порядок важен: валюта компании задаётся до первой проводки.** Odoo не даёт
сменить её, когда по ней уже есть записи в журнале, и это правильная защита —
пересчитывать историю задним числом нельзя. На боевой базе это значит: рубль
ставится при создании базы, до загрузки любых учётных данных. На стенде с
демо-данными Odoo валюта так и осталась долларовой.

**Российского плана счетов нет ни в ядре Odoo, ни в публичной части Rudoo.**
В ядре 226 локализаций, включая казахскую, российской среди них нет; в
публичном репозитории Rudoo `l10n_ru_base` — это базовый модуль с настройками,
без плана счетов. План счетов по приказу Минфина 94н, судя по всему, лежит в
закрытой части консорциума — это первое, что стоит у них запросить.

## Совместимость Rudoo с Odoo 19: что мы встретили

Найдено при развёртывании. Всё это код консорциума: чинить у себя означает
потерять правку при первом обновлении дистрибутива.

| Что | Следствие |
|---|---|
| `l10n_ru_contract` не объявляет зависимость `pymorphy2` | Штатная проверка зависимостей молчит, установка падает на середине транзакции |
| `pymorphy2` не работает на Python 3.11+ (`inspect.getargspec` удалён) | Модуль неработоспособен как есть; обошли заглушкой на `pymorphy3` в окружении |
| `l10n_ru_attorney`: `<odoo>` с лишним содержимым в `report/consent_report.xml` | Не проходит проверку XML в Odoo 19, не устанавливается |
| `report_weasyprint` требует библиотек GTK | На Windows не работает; на РедОС и АльтерОС ставится пакетом — это ограничение стенда, а не дистрибутива |

## Лицензия

LGPL-3, как у собственных модулей Rudoo. Обратите внимание: часть модулей дистрибутива — перепакованные модули OCA под **AGPL-3**, у которой сетевой копилефт. Если правите такой модуль и отдаёте его работу по сети, изменённый исходник надо опубликовать. Для наших `coop_*` этот вопрос не возникает, но при выборе, что дорабатывать, его надо держать в голове.

## Наполнение каталогов

Каждый каталог MVP — люди, организации, ресурсы, навыки, вакансии, проекты,
сделки, транзакции и прочие действия — должен содержать **не менее 100–200
правдоподобных записей**. На пяти демонстрационных строках не проверяются ни
поиск, ни фильтры, ни группировки, ни постраничная навигация, ни поведение
экрана под нагрузкой, поэтому раздел без такого наполнения не считается
готовым.

Записи генерируются с разбросом: настоящие города, осмысленные названия и
описания, разные даты, суммы и состояния — включая пустые, отменённые и
спорные. Одна строка, размноженная с разными номерами, каталогом не является.
